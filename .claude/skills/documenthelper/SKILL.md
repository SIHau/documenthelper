# 公文小幫手（AI 使用說明）

公文小幫手把公文拆成**結構化稿件（JSON）**，由程式負責自動編號、民國日期、版面與匯出，再用固定規則檢查格式與用語。AI 的工作是**把使用者的需求寫成稿件 JSON**，用命令列檢查、修正，最後匯出檔案。命令列使用的是和網頁版、桌面版同一份程式，結果與畫面完全一致；不使用 AI 判斷，檢查是固定規則。

## 先決條件

- 需要 Node.js 18 以上。
- 第一次執行時啟動器會自動在專案根目錄跑 `npm ci`（需要網路）。
- 所有指令都用啟動器：`bash .claude/skills/documenthelper/scripts/dh.sh <指令>`（以下簡寫成 `dh`）。skill 若被複製到專案外，先設定環境變數 `DOCUMENTHELPER_DIR` 指向公文小幫手專案根目錄。
- 相對路徑以呼叫時所在的資料夾為準；稿件檔可用 `-` 從標準輸入讀取。

## 標準流程

1. **釐清需求**：文種、發文機關、受文者、事由、要對方做什麼、日期、有無附件或限期。缺少關鍵資訊就先問使用者，**不要編造機關名稱、人名、發文字號或日期**。確實不知道的欄位先寫「○」，並在回覆中明講。
2. **選文種**：`dh types` 看各文種用哪些欄位；對照 [references/document-types.md](references/document-types.md)。
3. **起稿**：
   - 有現成範本就用 `dh templates` 找，再 `dh templates show <id> > draft.json`。
   - 否則 `dh new 函 --sender "機關" --recipient "受文者" --date 2026-11-09 > draft.json`，再編輯 JSON。
   - 稿件只需寫用到的欄位，其餘自動補預設值；分項不用寫 `id`。欄位說明見 [references/draft-schema.md](references/draft-schema.md)，範例見 `examples/`。
4. **撰寫內容**：先讀 [references/writing-guide.md](references/writing-guide.md)（依使用者提供的教學資料整理，每條規則標有出處）。需要原文時，到 [references/source/](references/source/README.md) 用 `grep -n "關鍵字" references/source/*.md` 查，解釋修正理由時請引用出處。
5. **檢查**：`dh check draft.json`。`錯誤` 必須全部解決（結束代碼 1 表示還有錯誤）；`注意` 要逐項處理或向使用者說明為什麼保留；`建議` 視情況採納。修改後重新檢查，直到沒有錯誤與注意。
6. **預覽**：`dh preview draft.json` 顯示純文字版面（含自動編號、民國日期、對齊），回覆時可貼給使用者確認內容。
7. **匯出**：`dh render draft.json --format pdf --out ./out`（`--format` 可為 `pdf`、`odt`、`docx`、`all`）。檔名預設是發文字號；沒有發文字號則為「文種_日期_主旨前 15 字」。把產生的檔案路徑告訴使用者。
8. **交付稿件檔**：匯出時一併保留 `draft.json`（就是「稿件檔」），使用者可在公文小幫手「稿件 → 開啟稿件檔」匯入繼續編輯。

## 指令速查

| 指令 | 用途 |
|---|---|
| `dh types` | 文種清單與各文種使用的欄位 |
| `dh new <文種> [--sender --recipient --date --direction]` | 產生空白稿件 |
| `dh templates` / `dh templates show <id> [--date]` | 內建範本清單／由範本產生稿件（日期預設今天、發文字號清空） |
| `dh phrases [上行｜平行｜下行｜斜行]` | 期望語與常用句型 |
| `dh check <稿件> [--json]` | 格式與用語檢查 |
| `dh preview <稿件>` | 純文字版面預覽 |
| `dh normalize <稿件>` | 補齊欄位後輸出完整稿件 |
| `dh render <稿件> [--format] [--out]` | 匯出 PDF／ODT／DOCX |
| `dh filename <稿件> <副檔名>` | 顯示匯出檔名 |
| `dh deadline --date --urgency [--limit]` | 辦理期限（最速件 1、速件 3、普通件 6 個工作天；限期較早時以限期為準） |
| `dh docnumber --word 字別 --date [--used 字號,字號]` | 產生下一個發文字號（字號格式：字別＋第＋民國年三碼＋月日＋當日流水號三碼＋號） |
| `dh law <法規.txt>` | 把法規純文字解析成條文，可用來填草案對照表 |

## 重要原則

- **內容正確優先於格式**：事實、日期、金額、法條都要以使用者提供的為準。引用法規條文時，請使用者提供條文或確認，不要憑記憶引用。
- **格式問題交給程式**：不要自己手寫「一、」「(一)」編號、不要在文字裡寫西元日期的欄位（`date` 用 `YYYY-MM-DD`，程式會轉成民國年）、不要自己排版對齊或縮排。分項只用 `level`（0＝一、 1＝(一) 2＝１、（全形） 3＝(１) …），不要在文字裡自己寫編號。說明或辦法**只有一項時不分項**，程式會把它緊接在段名後；案情簡單只寫 `subject`（一段式）。
- **限期寫進主旨，速別留空**：有辦理或復文期限時，主旨寫「…，於115年11月20日前辦理，請查照。」，稿件 `limit` 填日期、`urgency` 留空（檢查會提醒）。
- **行文方向有四種**：`上行`（鈞、請鑒核）、`平行`（貴、請查照）、`下行`（貴、請照辦）、`斜行`（對無隸屬關係的較高級機關，稱「大」）。
- **內文中的日期用民國年**，例如「中華民國115年11月20日」；檢查會對西元年份提出注意。
- **交付前不能留「○」**：檢查會提醒尚未填寫的「○」。除非使用者明確要範本或草稿，否則要補齊或回頭詢問。
- **檢查規則是常見慣例，不是官方標準**：例如各行文方向適用的期望語、主旨建議字數、口語詞清單，都可能與使用者機關的習慣不同。使用者有指定寫法時以使用者為準，並說明檢查提醒的原因。
- **PDF 字體**：本文用思源宋體、簽名用 Yuji Boku，都已嵌入 PDF；若有字體沒有的字元會在標準錯誤輸出列出並略過，請改寫。ODT／DOCX 只記錄字體名稱（本文標楷體），對方電腦需安裝才會一致。
- **辦理期限只排除週六日**，不含國定假日；回覆時要註明這點。
- 不要把使用者的稿件內容、機關或人名資料送到其他外部服務；所有處理都在本機完成。

## 常見狀況

- `找不到字體套件`：在專案根目錄執行 `npm ci`。
- `這不是公文稿件檔（找不到文種）`：稿件 JSON 缺少 `type`，或文種名稱不在 `dh types` 清單內。
- 檢查回報「主旨結尾缺少期望語」：函、書函的主旨結尾要有「請查照」「請鑒核」等；公告、簽、開會通知單不需要。
- 需要學生議會的議案、審查報告對照表、會議紀錄、簽到表、概算書：這些文種的欄位較多（`motion`、`minutes`、`budget`），見 [references/draft-schema.md](references/draft-schema.md) 與 `dh templates` 內的 `council-*`、`motion-*` 範本，建議以範本為底修改。
